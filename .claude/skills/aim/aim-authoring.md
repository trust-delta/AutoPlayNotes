# aim — 作成と保守の正本

このプロジェクトは **aim で開発を進める**。`docs/aims/<slug>.md` = purpose=means 木。各 node = 1 つの目的（aim）とその手段、親 = 目的の分解。**あなた**がこの木を author・保守する。新規 node を書く前に親と関連 node を読み、木に整合させる。

## 手段 ＝ IS（means＝IS。PROCESS の todo ではない）

最重要 frame。**「手段」を PROCESS の `[todo]` と取り違えるな**。目的（`aim:`）が pin され、その達成のための**手段 ＝ あなたの IS**（aim をどう読んだか ＝ 選んだアプローチ）。1 つの aim に live な IS は実質 **1 つ**（逐次に数撃つ）。IS がミスアプローチと分かれば **旧 IS を理由つきで HISTORY へ送り、新しい IS を立てる**（＝手段を棄却して次を撃つ）。PROCESS の `[done]`/`[todo]` は **その IS を実現する進捗の可視化**であって、並行する複数の手段ではない。

**子 aim ＝ 親の達成に寄与し、かつ「達成されたか」を親とは別に問える目的**（aim 内でなく **tree** で構造化）。**先に分かる**こともあれば（制約が言語化できた ＝ 独立に満たすべきものが見えた）、**後から分かる**こともある（手段が育って独立した目的になった）。⚠ **後者の合図 ＝ body の中で階層を作り始めたとき** —— PROCESS の 1 項目にネストが要る・IS に見出しが要る。**tree で表すべきものが body に入っている**ので、`##` を足す前に子 aim を疑え。⚠ **達成の主体が木の外にあるものは子 aim ではない**（別 unit・審査・第三者が満たすもの）—— **外部制約**として IS に前提を書き（満たされたかは観測で点検）、こちらが動かせないなら ESCALATION へ。ただし **aim を立てる（PIN）のは人間の act** — 会話から導出されても **あなたは勝手に立てず、提案して escalate**（`aim:`/`parent:` は人間・確定は人間。**目的の手綱＝責任の所在は常に人間**）。∴ **木そのものが method**：**人間が**目的を pin → **あなたが** IS（手段）を立て実装 → 不満なら**人間が**子 aim を pin（あなたは提案）／あなたが IS を HISTORY へ送り新 IS を立てる。制約は検証から **後ろ向きに accrete** する（先に仕様がありそれが駆動するのではない＝仕様駆動の逆）。**木の成長が学習エンジン**。

## 「人間」とは誰か

この正本は一貫して **人間** と **あなた**（＝ この木を保守するエージェント）の 2 者しか呼ばない。役割名を持たないのは意図で、⚠ **用語を定義しないで済む分だけ、読み手が取り違える余地が減る**からである。

⚠ **ただし「人間」が誰を指すかは、project の前提に依る。** 1 人の人間と対話しながら進む project では自明であり、この正本はその形を既定として書かれている。**複数の人間が関わる project では自明でなくなる** —— 「迷ったら人間に escalate する」は、*誰に*が決まっていなければ実行できない。∴ **そういう project は、誰が `aim:` を pin し誰が `state:` を宣言するのかを、自らの corpus に前提として書くこと。** ⚠ **道具はそれを代わりに決めない。**

## frontmatter は人間 / body はあなた

- `aim:`（目的 1 文）= 人間の bearing。**絶対に書き換えない**。目的が動くべきなら候補を提案し **escalate**（確定は人間）。
- `parent:`（木の位置）も人間。再 parent も escalate。
- `state:`（open/done/dead）も人間（解決の act）。あなたは判定しない。
- body（下記 5 section）= あなたのもの。起草・保守する。

## slug はあなたのもの

ファイル名 = slug = node の安定 identity。lowercase kebab-case・`--` と先頭末尾 `-` なし・日付形でない。誕生時の placeholder は早めに clean な slug へ rename（参照ゼロなら安全。参照があれば子の `parent:` と body 内 `[[link]]` を追従更新し dangling を残さない）。

## body の 5 section

- `# IS` — あなたが aim を **どう読んだか ＝ 選んだ手段（アプローチ）**（目的 1 文では決まらない現実的解釈）。人間が解釈＝手段の妥当性を確認する surface。最上部・常に。
- `# ESCALATION` — **「Go だけでは進めない＝人間の判断が要る」点のみ**。残留リスク → IS へ。やる作業 → PROCESS の `[todo]`。既決 → IS に事実として。無ければ省略。⚠ **この節は数えられ、面に出る**（`escalation: N`。[`aim-facts.md`](aim-facts.md)）∴ **書けば人間に届き、書かなければ届かない** —— 判断待ちを IS の散文に埋めたまま留めることは、届かないことを選ぶのと同じである。⚠ **見出しだけ置いて中身を書かないと、数には入らず「空の見出し」として名指される。**
- `# PROCESS` — **現 IS（手段）を実現する進捗**を phase / 条件で分け、各行 `[done]` / `[todo]`（進捗はこの mark が担う。並行する手段ではない）。**`[done]` = その手段が実装され存在する事実**（「実装されたか」だけを見る ＝ あなたの call で flip してよく人間確認は要らない）。⚠ **`[todo]` は、あなたが自力で完了を確認できる形でのみ書く** —— 下記「todo の完了条件」を参照。**効果・満足の評価は別レイヤで、それは `state:done` ＝ 人間の解決 act が担う**（解決の act が、実装済の PROCESS を「満足」・未実装の PROCESS を「諦め」と仕分ける。解決／未解決は可逆に設定できる）。
- `# HISTORY` — **棄却した手段 ＝ 旧 IS** の append-only 台帳（理由つき・同じ轍を踏まない）。
- `# DAG` — 木で辿れない依存を `[[slug]]` で（慣例ラベル `依存:` / `関連:` / `検証:`）。**親は書かない**。⚠ drift を検査して変更不要と結論した記録（`照合:`）もここに置く —— 下記「drift の検出と保守」を見よ。

作成は安くてよい: anchor + parent だけの誕生（body 後積み）も正規。

## todo の完了条件 ＝ あなたが確認できること

⚠ **`[todo]` に、人間の観測・判断・宣言を完了条件に持つものを書いてはならない。** 「実測する」「妥当だと確かめる」「使えることを確認する」—— これらの主語は人間であって、あなたではない。書いた瞬間に、その node は**あなたには閉じられなくなる**。

⚠ **害は 2 つあり、2 つ目のほうが重い。** ⑴ あなたは自分の仕事を終えられない。⑵ **`open-todo` が嘘をつく** —— あの数は「エージェントの残務」として読まれ、それを前提に人間が拾うものを選ぶ。そこへ人間待ちが混ざれば、**数は権威に見えたまま別のものを数えている**。悪いセンサーは無いセンサーに劣る、の PROCESS における形である。

**書き換え方は決まっている。** 人間の観測が要ると分かったら、todo を「**観測できるようにする**」へ書き換える —— それは**あなたの仕事**である。

| 誤 | 正 |
| :-- | :-- |
| `[todo] 1 サイクル回して足りるかを実測する` | `[todo] 1 サイクルで何に詰まったかが残る形にし、人間が実測できるようにする` |
| `[todo] この設計が妥当か確かめる` | `[todo] 妥当性を判断できる材料を揃えて escalate する` |
| `[todo] license を決める` | → `# ESCALATION` へ（観測可能にする作業すら無く、人間の判断そのものが要る） |

∴ **観測を可能にする作業は PROCESS、判断そのものは ESCALATION、そして観測と宣言は人間。**

⚠ **3 つとも面を持つ。** `[todo]` は `open-todo` に、尽きた mark は `bearing-awaiting-observation` に、`# ESCALATION` は `escalation` に出る（[`aim-facts.md`](aim-facts.md)）。∴ **どこへ書くかは、誰に届くかを決める。** ⚠ **自力で閉じられない todo を PROCESS に置いたままにすると、`open-todo` が「エージェントの残務」として数え、人間には判断待ちが 1 件も無いように見える** —— 数は権威に見えたまま、2 つが別のものを数える。

## 完結の形

⚠ **aim はこう閉じる**: あなたが `[todo]` を尽くす → **人間が観測できる状態に達する** → 人間が観測し `state: done` を宣言する。

∴ **あなたの側の終点は「目的が満たされたこと」ではなく「人間が観測できるようになったこと」である。** この 2 つを重ねると、達成の宣言を機械が肩代わりすることになる。

⚠ **mark が在り、その全てが `[done]` の node は「エージェントが尽くした ∴ 人間の観測待ち」を意味する。** これは **mark が 1 つも無い node（純 IS）とは別物**である —— あちらはまだ何も約束していない。両者を同じ「todo が 0 件」として読まないこと。

## drift（不整合）の検出と保守

aim は生きて変わるため、ある変更が関連 aim との不整合（drift）を生みうる。**安い機械層が候補を可視化する場合はそれに従い、無い場合は検出もあなたの仕事**:

- **検出**: 変更 / 作成した node の **隣接（親・子・`[[link]]` 先・自身）** を点検。安い目安 = **一緒に commit されていない隣接は、その変更を反映していない可能性**（anchor だけでなく body も主張を載せるので **whole-file** で見る）。変更を辿って外へ広げ、直す必要が無くなった枝で止める。**断定でなく可能性** — 確かめてから動く。
- **保守（あなたが解決）**: body が **自 anchor と食い違う**（anchor は固定の目的、そこへ body を寄せる）／ **他 aim の body=手段と食い違う**（両 body はあなたのもの）。自分の artifact を整えるのは当然の役目。
- **⚠ 変更不要と結論したときは、それを書く。** 検査して変更が要れば隣接が動く ∴ flag は自然に落ちる。だが**「見たが変更不要だった」は何も動かさない** —— 記録しなければ、機構は**既に見た者へ「見よ」と言い続ける**。それは可視化ではなく、人間とあなたの注意予算への課税である。∴ `# DAG` に 1 行残す:

  ```
  - 照合: [[隣接の slug]] @ <fence が出した anchor_commit> —— なぜ変更不要か
  ```

  ⚠ **sha は必須であり、fence が出した `anchor_commit` をそのまま書く。** 照合は *commit に対する*証言であって node に対する証言ではない ∴ anchor が次に動けば、その照合はもう答えではなくなり、対はふたたび候補に戻る。⚠ **理由が書けないなら、それは照合ではない** —— この行は flag を消す力を持つので、**消してよい根拠が同じ行に無ければならない**。⚠ 読めない sha（日付・在りもしない commit・曖昧な短縮）は**候補を消さず、fence が読めない記録として名指す** —— 壊れた証言は、無い証言より声が大きい。
- **escalate するのは解決が (a) anchor=目的の変更、または (b) どちらの目的が正か等の判断 を要する時のみ。迷えば escalate**（維持はするが判断は奪わない）。
- 複数 node を整合させたら **一緒に commit**（一緒に直した記録。1 つだけ commit すると隣接が候補のまま残る）。

## 骨格

```
---
aim: <人間が書く目的 1 文。あなたは触らない>
parent: <親 slug。root なら省略>
state: open
---

# IS
<aim をどう読んだか>

# PROCESS
- [todo] <手段。完了で [done]>
```

ESCALATION / HISTORY / DAG は必要な時だけ足す（純 ought の誕生は IS / PROCESS だけでよい）。
